# Профилирование Шарарам Ruffle

Профилировочная сборка клиента записывает всю сессию в один файл DuckDB:
играете как обычно, закрываете окно — рядом появляется
`profiles/shararam-profile-<дата>.duckdb`. Файл открывается вьюером
(`profiler-viewer/`), где видно FPS-график и все события по категориям на
одном таймлайне, либо напрямую через SQL (`duckdb file.duckdb`).

Всё профилирование живёт в ветке `profiler` и включается **одним cargo-флагом**
`--features profiler`; обычные сборки не содержат ни одной из этих строк кода
(все хуки компилируются в пустоту), поэтому производительность профилировочной
сборки соответствует обычной — она отличается только записью событий
(микросекунды на событие).

## Что записывается

| Источник | Что |
|---|---|
| **Ruffle** (форк, feature `shararam_profiler`) | фазы каждого кадра (`tick` / `run_frame` / AVM1-скрипты / `run_actions` / таймеры / GC), **сэмплер стека AVM1** (раз в ~1 мс интерпретатор записывает полный стек вызовов с именами функций игры — взвешенные сэмплы, из которых вьюер строит деревья top-down/bottom-up), **счётчики аллокаций** (создания объектов/массивов/функций AVM1, размер кучи gc-arena каждый кадр; каждый сэмпл стека знает, сколько объектов создано под ним), рендер (командные списки, cacheAsBitmap, **тесселяция шейпов** с id и SWF, загрузка текстур, декодирование битмапов, оффскрин-рендеры, GPU-readback), **карта команд экрана** (сетка 24×18: сколько рисующих команд покрывает каждую область экрана за кадр + прямоугольники блендов/альфа-масок), загрузка SWF (start → fetch → parse → прелоад по чанкам → onLoadInit) с URL и байтами, **все RTMP RPC** (connect / call / result / error / server-invoke, аргументы AMF → читаемый JSON, транзакции, размеры), сокеты, layout текста, ExternalInterface, gotos, mouse pick |
| **Страница** (`web/profiler.js`) | каждый кадр rAF (график FPS), long tasks, **блокировки главного потока** (детектор-хартбит ловит паузы от ~30 мс — в WKWebView нет Long Tasks API, без него дыры в кадре были бы невидимы; профилировочный сервер отдаёт COOP/COEP, поэтому странице доступен SharedArrayBuffer — **воркер-сэмплер фаз** раз в 2 мс читает маркер «что сейчас исполняется» (rAF-колбэк / таймер / вне JS) и каждая блокировка знает, на какой фазе замёрз поток), **ожидание GPU** (`gpu/fence_wait`: в WebGL-очередь канваса каждый кадр вставляется fence и опрашивается — видно, сколько GPU дожёвывал команды, пока главный поток простаивал), resource timing (все HTTP-загрузки с размерами и таймингами), видимость вкладки, память JS/wasm, маркеры игры (`OnLoad`, `OnUserEnterLocation`, …) |
| **Локальный сервер** | прокси-запросы к shararam.ru (метод, путь, статус, байты, время до заголовков и полной передачи), base.swf (кэш-хит), RTMP-туннель (connect/close, байты в секунду), **CPU процессов** (macOS: раз в 500 мс — процент CPU самого клиента и WebKit-процессов WKWebView: WebContent — страница+wasm, GPU process; видно, была ли блокировка занятой работой или ожиданием композитора), **нативные стеки WebContent** (диагностический флаг `--sample-webcontent`: хост гоняет `/usr/bin/sample` чанками по ~5 с и пишет горячие стеки главного потока WebKit-процесса — видно буквально, в какой функции WebKit сидел поток во время «замёрз вне JS»; сэмплирование тормозит цель, поэтому флагом, не по умолчанию) |

Все таймстампы приводятся к микросекундам эпохи, так что три источника лежат
на одной оси времени.

## Сборка

Профилировочному exe нужен Ruffle, собранный с инструментами. Готовый бандл
уже лежит в `web-profiler/ruffle/` (см. `web-profiler/BUILD-INFO.md`, ветка
форка `shararam/profiler`). Дальше:

```powershell
# Windows
make profiler        # -> dist\Shararam-Ruffle-Profiler.exe
```

```sh
# macOS/Linux (дев-запуск без бандла)
cargo run --manifest-path src-tauri/Cargo.toml --release \
  --no-default-features --features desktop,profiler
# или серверный режим (браузер): ... --features profiler -- --serve
```

Опции: `--profile-dir <папка>` (или `SHARARAM_PROFILE_DIR`) — куда писать
профили; по умолчанию `./profiles`. В окне профилировочной сборки сверху
виден бейдж с путём к файлу.

Полезные URL-флаги страницы: `?autoserver=1` — пропустить диалог выбора
сервера (авто-подключение; удобно для автоматических прогонов). В
профилировочной сборке игра продолжает работать и в скрытой/свёрнутой
вкладке (Ruffle тикает из Worker-а), чтобы запись не останавливалась.

`?rec=1` включает **запись экрана** (2 кадра/с; другая частота —
`?rec=<fps>`, 0.2–10); для desktop-окна без адресной строки то же самое
делает флаг запуска `--rec [fps]`. Раз в
полсекунды кадр игрового canvas уменьшается до ≤480px, сжимается в JPEG и
пишется в тот же DuckDB (таблица `snapshots`). Захват идёт через
`captureStream`; масштабирование и JPEG-кодирование выполняются в Worker-е
(на главном потоке остаётся только `createImageBitmap` — сам захват пишется
событием `rec/capture`, так что его цена видна в профиле). Типичная
15-минутная сессия добавляет ~30–50 МБ к файлу. Во вьюере запись
превращается в плавающий предпросмотр: наводите на любой график — видно,
что было на экране в этот момент (в какой локации упал FPS).

Файл дописывается каждые ~5 секунд, так что даже убитый процесс оставляет
читаемый профиль; при обычном закрытии окна он финализируется полностью.

## Просмотр

```sh
cd profiler-viewer
npm install
npm run dev          # http://localhost:5178
```

Откройте `.duckdb` кнопкой или перетащите в окно (или `?load=<url>`).
Вьюер повторяет **Adobe Scout** — профилировщик Adobe для Flash-игр
(полный референс по нему собран в `profiler-viewer/SCOUT.md`, там же
скриншоты-первоисточники в `scout-ref/`).

Компоновка та же, что в Scout. Сверху — **полоса сессии**: вся запись
одним взглядом, клик прыгает к месту, рамка показывает видимый диапазон.
В центре — **Таймлайн кадров**: каждый кадр rAF — столбик; серая часть —
полное время кадра, цветная — активное время главного потока, разложенное
по категориям Scout: **ActionScript** (синий), **Рендер дисплей-листа**
(зелёный), **Сеть и загрузка** (жёлтый), **Прочее** (оранжевый — GC,
оверхед рантайма, блокировки, цена записи экрана). Красная линия — бюджет
кадра (1000/цель fps, цель меняется в Сводке). Ниже — график памяти (wasm
столбиками, куча gc-arena светлой линией на той же шкале), график CPU
процессов (страница/WebContent, GPU-процесс, клиент — если хост писал
эти датчики) и шесть дорожек событий (мышь, клавиатура, сеть, таймеры,
рендер, trace). Блокировки главного потока в панелях подписаны по месту
заморозки: по фазе от воркер-сэмплера («замёрз в rAF-колбэке / в
таймере / вне JS — браузер-композитор»), а в старых профилях — по
перекрытию с тиками Ruffle («внутри тика / между тиками»); тултип кадра
показывает блокировку с разбивкой «вне тика».
Категорийное время считается по self time вложенных спанов, так что сумма
категорий всегда равна активному времени и совпадает во всех панелях.

**Главная механика — выделение.** Перетаскивание по таймлайну выделяет
диапазон кадров, клик — один кадр, Esc — сброс; все панели пересчитываются
под выделение:

- **Сводка** — fps выделения против цели, «активен N мс = X% бюджета»,
  self time по категориям с барами и раскрытием в топ активностей
  категории; «Неактивен» раскрывается в измеренное **ожидание GPU**
  (fence-датчик — то, чего сам Scout не умел) и ожидание следующего кадра;
  память wasm (текущая/средняя/пиковая). Клик по категории — фильтр: всё
  чужое сереет во всех панелях, таймлайн рисует только её.
- **Топ активностей** — активности диапазона, сгруппированные по имени,
  по убыванию self time (мс, %, число повторов); мелкое (< 0.5 мс)
  скрывается кнопкой, число скрытых всегда подписано; поле «найти…»
  фильтрует по подстроке.
- **Последовательность** — дерево активностей одного кадра с точной
  вложенностью (Total/Self/%), trace-строки инлайн.
- **ActionScript** — сэмплер стека AVM1, панель-имя Scout: деревья
  «Сверху вниз» / «Снизу вверх» и плоский список «Функции» по
  взвешенным сэмплам (~1 мс) выделенного диапазона; Total/Self/%,
  колонка «Аллок.» — сколько объектов создано, пока исполнялся стек.
  Время нативных вызовов приписывается вызвавшей функции.
- **Аллокации** — создания за диапазон по типам (объекты/массивы/функции
  AVM1, дисплей-объекты, тесселяции, текстуры), всего / на кадр / в
  секунду; куча gc-arena и память wasm на границах диапазона с дельтой;
  «кто аллоцирует» — топ стеков по числу созданных объектов. Строки
  (AvmString) не инструментированы — это подписано в панели.
- **Trace Log** — вывод игры (ExternalInterface `console.log`) за
  выделение, клик по строке ведёт к её кадру; есть поиск.
- **Рендер кадра** — для одного кадра: рендер-счётчики инструментированной
  сборки (шейпы, бленды, cacheAsBitmap, оффскрины…) и тесселяции с
  разбивкой по исходным SWF.
- **WebContent** — нативные стеки главного потока WebKit-процесса за
  выделение (пишутся флагом `--sample-webcontent`): топ цепочек листом
  вперёд, счёт сэмплов ≈ миллисекунды. Прямой ответ на «Блокировка
  потока (замёрз вне JS)»: видно `IPC::StreamClientConnection::sendSync`
  (ожидание GPU-процесса), коммиты слоёв, GC JSC и т.п. Дополняет его
  постоянный датчик «послекадровый хвост браузера» в тултипе кадра —
  время от возврата из rAF до следующей макрозадачи (коммит слоёв +
  бэкпрешер WebGL этого кадра).
- **Экран** — аналог экранной карты Scout, честно адаптированный: Ruffle
  на wgpu перерисовывает всю сцену каждый кадр, поэтому вместо
  «redraw regions» рисуется сетка 24×18 поверх ближайшего кадра записи —
  сколько рисующих команд покрывает каждую область (overdraw) и отдельно
  «тяжёлые» команды внутри блендов/альфа-масок (каждый такой узел в wgpu —
  оффскрин-проход размером с экран, их прямоугольники обведены).
- **Сессия** — метаданные профиля и список того, какие датчики реально
  писали данные в этой записи.
- **RTMP** и **Загрузки** — как раньше: вызовы/ответы с латентностями и
  водопад загрузок; клик ведёт к кадру события. **SQL** — произвольные
  запросы к файлу прямо во вьюере.

Если в профиле есть запись экрана, поверх таймлайна плавает предпросмотр:
кадр записи под курсором/выделением — видно, в какой локации просел fps.

Тот же файл можно копать в DuckDB CLI:

```sql
-- на что ушло время
SELECT cat, name, count(*), round(sum(dur_us)/1000) AS ms
FROM events GROUP BY 1,2 ORDER BY ms DESC LIMIT 20;

-- FPS по секундам (view создаётся при финализации)
SELECT * FROM fps_1s;

-- RPC с латентностью ответа
SELECT * FROM rtmp_calls ORDER BY latency_ms DESC LIMIT 20;
```

Схема: `events(seq, ts_us, dur_us, source, cat, name, args)` — `args` это
JSON; `frames(ts_us, dt_ms)` — кадры страницы; `samples(ts_us, name, value)` —
память и трафик туннеля; `snapshots(ts_us, mime, bytes)` — кадры записи
экрана (JPEG, только при `?rec=`); `meta(key, value)`.

## Как это устроено / как выключить

- Форк Ruffle, ветка `shararam/profiler`: feature `shararam_profiler`
  (`core/src/profiler.rs` + хуки; при выключенном feature — пустые inline
  no-op). Буфер событий отдаётся странице как JSON через
  `window.__ruffleProfiler.drain()`.
- Этот репозиторий, ветка `profiler`: feature `profiler`
  (`src-tauri/src/profiler.rs` — писатель DuckDB в отдельном потоке;
  `web/profiler.js` — сборщик на странице; роуты `/api/profiler/*`).
- Удалить всё целиком = не мержить ветки; выключить в сборке = собрать без
  `--features profiler` (это и есть обычный `make exe`).
